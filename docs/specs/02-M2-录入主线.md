## 架构总图（任务对照）

```
入口A 拍处方笺                          入口B 拍药品
  POST /api/intake/prescription           POST /api/intake/drug
    │                                        │
  ① detectLayers ── 校验：须含处方层        ① detectLayers ── 校验：须含药盒层
    │   （不符→409 LAYER_MISMATCH，可切换）    │   （医院标签层→返回提示标志）
  ② runOcr（处方层）                        │
  ③ cropBody（L0 版面裁剪）                  │
  ④ parseWhitelist（L1 白名单）              │
  ⑤ sanitizeScan（L2 兜底）                  │
  ⑥ verifyBacklink（模型兜底值回链校验）      │
    │                                        │
  身份线（并行）：VLM 提取 → 三项严格匹配 ←───┘
    │
  ⑦ buildDraft：档案草稿+计划草稿+健康建议+相互作用+范围校验
    │
  确认页（前端）→ POST /api/drafts/:id/confirm → 事务写 drugs+plans+sources+health_profiles
```

**管线铁律**（技术方案 §6）：①–⑦ 每一步是**独立纯函数**，输入输出全量可 mock，单测覆盖；编排层串行调用。任何一步不过 → 降级（原文人工补 / 手动建档），**绝不预填猜测**。

## T1. AI 客户端层（`src/lib/ai/`）

**做什么**

1. `qwen.ts`：Qwen3-VL 调用封装（层检测 + 身份线提取共用），`QWEN_BASE_URL/QWEN_API_KEY` 从 env；超时 30s、1 次重试、失败抛 `AIUnavailableError` → 上层降级路径；
2. `ocr.ts`：按 M1-T11 定案的 OCR 引擎封装，输出统一 `OcrResult { chars: [{ text, confidence, box{x,y,w,h} }] }`（字符级，硬要求）；
3. `baichuan.ts`：Baichuan-M3-Plus 封装（M2 仅用于兜底解析；咨询在 M3 强化）；
4. 三个客户端实现**统一的 `AiClients` 接口**，管线 `run.ts` 经**依赖注入**使用（不直接 import 具体实现）——这是 E2E fixture 回放的唯一接缝（见 T10）；生产组装真实实现，测试注入 mock/fixture 实现；
5. 所有客户端：请求 body 组装函数独立可测（验证"只含白名单字段"），日志不打原文。

**完成标准**：三个客户端各有"请求体组装 + 错误映射"单测（不真调 API，fetch mock）；`AIUnavailableError` 冒泡路径有测试。

## T2. 脱敏纯函数（`src/services/sanitize/`）—— L0/L1/L2/L3

**做什么** 以 `demo/server/index.js` L1/L2 段为参照重写为 TS 纯函数（demo 逻辑已验证可用）：

1. **L0 `cropBody(ocrResult)`**：锚点定位（`Rp` / `临床诊断` / `处方完毕`，锚点容错：大小写/空格/半全角），返回正文区字符集合与裁剪框 box；前记后记字符整块丢弃。锚点缺失 → 返回 `null`（走人工补）；
2. **L1 `parseWhitelist(bodyText)`**：正则模板解析（"每次X / 每日X次 / 共X天"等，从 demo 正则迁移并扩充），输出 `PrescriptionWhitelist`（`.strict()` 闭合 schema，shared 已定）；解析不全的字段标 `needsManual: true`，不猜；
3. **L2 `sanitizeScan(fields)`**：手机号/身份证（含校验位验证）/地址模式匹配，命中替换 `[已脱敏]` + 返回审计 `{ [type]: count }`（不记原文）；宁可误杀；
4. **L3 出口约束**：审计中间件/工具函数——`redactForLog(obj)` 用于一切日志出口；`assertNoPii(text)`（正则断言，供零泄漏测试复用）。

**完成标准**：每一层独立单测 ≥ 6 case（含 PRD golden case 的涂黑/遮挡变体）；L2 对"正确手机号/带校验位身份证"必中，对"6 位数字"不误杀药名剂量；`assertNoPii` 在零泄漏测试中被复用。

## T3. 回链校验与兜底解析

**做什么**

1. `verifyBacklink(fields, bodyText)`：模型兜底解析（Baichuan）产出的每个值，必须在 L0 裁剪后的正文中**逐字可寻**（先做去空白/全半角归一）；找不到的字段丢弃并标 `needsManual`，记回链拦截计数；
2. 兜底解析编排：仅当 ④ 正则解析有缺项时触发；发给 Baichuan 的内容**只含白名单文本**（M2-T1 请求体组装单测保证）。

**完成标准**：`verifyBacklink` 单测 ≥ 5 case（含"模型改写了药名"必须被拦截）；兜底链路集成测试：正则失败 → 兜底 → 回链通过/拦截两条分支。

## T4. 层检测 + 身份线（`src/services/identity/`）

**做什么**

1. `detectLayers(image)`：Qwen3-VL 调用 → zod 枚举 `z.enum(['处方层','医院标签层','药盒原装层','说明书层','不支持'])` `safeParse`，多选数组；解析失败 = 层检测失败（明确报错，不猜）；
2. `extractIdentity(image)`：VLM 提取 `{ genericName, brandName?, specification?, form?, manufacturer?, otcFlag? }` → zod safeParse；
3. `matchDrugMaster(identity)`：对 `drug_master` 做**药名+规格+剂型三项严格匹配**（PRD §8.2）：
   - 归一化比对（规格解析成 `{value, unit}` 再比，"0.1%（10mL:10mg）"类拆解）；
   - 唯一匹配 → `unique`；多候选 → `ambiguous`（带候选列表）；药名命中但规格/剂型冲突 → `conflict`（带冲突详情，如"库 0.2% vs 提取 0.1%"）；
   - 批准文号仅作平局裁判：多候选时如 VLM 提取到批准文号则一锤定音，否则不阻塞进冲突清单；
4. 药盒层**永不提取用法用量**（结构上该函数就没有此输出字段）。

**完成标准**：`matchDrugMaster` 纯函数单测 ≥ 8 case（唯一/多候选/规格冲突/剂型冲突/批准文号裁决/无匹配）；`detectLayers` 与 `extractIdentity` 的 safeParse 失败分支有测试（mock 非法模型输出）。

## T5. 规则引擎（`src/services/rules/`）

**做什么**（参照 demo `/api/interactions`、`/api/draft-check` 逻辑）：

1. `checkInteractions(userDrugIds)`：对象是**生效计划集合**（status=active、时间窗与今日重叠的药品），对 `interaction_rules.drugIds` 做集合匹配；返回 `{ level, note, source, drugNames }[]`，四级枚举 `禁忌>慎用>需监测>注意`；未覆盖时返回明确的 `coverageNote`（"未覆盖 ≠ 无风险"）；
2. `checkDosageRange(planDraft, packageInsert)`：对照说明书库 `dosage` 结构化数字（`frequencyPerDay` / `dosePerUse` / `maxFrequencyPerDay`），超范围项返回 `{ field, planValue, insertMax, insertNote }`；仅标注留痕，**不阻止创建**（PRD §8.3）；
3. 接入 M1-T7 的 `POST /api/plans`：手动建计划也跑这两个检查，结果随响应返回（前端展示）。

**完成标准**：两引擎各 ≥ 6 单测（含海露 0.1% golden case：1 滴×4 次/日 ≤ 10 次/日 上限通过；超标场景正确标注）；集成测试：为已有生效计划的老药建新计划（续方）触发检查。

## T6. 管线编排 + 草稿 API

**做什么**

1. `src/services/pipeline/run.ts`：编排 ①–⑦ + 身份线并行；每步产出挂到草稿上下文；单步失败不炸整体，转成对应 `needsManual`/降级标记；全程 OCR 原文只在内存流转（L3）；
2. 草稿模型：新表 `drafts`（`id / userId / type('prescription'|'drug') / status('pending'|'confirmed'|'rejected') / payload jsonb / createdAt`），payload 内含：档案草稿、计划草稿（含四类标注）、冲突清单、健康信息建议、相互作用与范围校验结果、人工补字段清单、裁剪图引用；
3. API：
   - `POST /api/intake/detect`：仅层检测（入口校验独立暴露）；
   - `POST /api/intake/prescription`：入口A 全管线 → N 个条目拆 N 份草稿（PRD §7.2.1），响应草稿 id 列表 + 每份概要；
   - `POST /api/intake/drug`：入口B 仅身份线 → 1 份建档草稿；检测到医院标签层时 payload 带 `labelNotice: true`（前端展示"标签用法不自动抄录"提示）；
   - `GET /api/drafts/:id`：草稿详情（原文对照数据：裁剪图 base64/静态引用 + 低置信字符坐标）；
   - `POST /api/drafts/:id/confirm`：**单事务**原子写 `drugs + plans + sources + health_profiles(勾选项) + drafts.status` + 确认留痕 `{confirmedAt, method, keyFieldsSnapshot}`；医嘱字段如用户有修正，落 `user` 标注；
   - `POST /api/drafts/:id/reject`：status=rejected 留痕。
4. 层检测结果与所选入口不符 → 409 `{ code:'LAYER_MISMATCH', detected:[...], suggestion }`，**不静默改道**；不支持对象 → 422 `UNSUPPORTED_OBJECT` + 统一安全提示文案。

**完成标准**：管线集成测试（全 mock AI）：成功路径产出正确草稿；OCR 失败/裁剪失败/解析不全三条降级路径产出 `needsManual` 草稿；confirm 事务测试（写四表 + 中途失败回滚不留脏数据）；LAYER_MISMATCH / UNSUPPORTED_OBJECT 分支可测。

## T7. 确认页前端（`/drafts/:id`）

**做什么** 以 `demo/src/pages/Confirm.tsx` 为参照，是**唯一闸门**（PRD §7.2.5）：

1. 原文截图 ↔ 结构化字段**并排**（裁剪图可放大，低置信字符标红下划线）；
2. 用量/频次/疗程**无差别逐项核对**（不因置信度高跳过）；每项带四类标注徽章（TAG_META）；`needsManual` 字段显示原文该行 + 空输入，绝不预填；
3. 冲突清单（多候选/规格冲突，系统不选边，用户可手动从候选中选或改手动建档）；
4. 时间点确认：`suggestTimes` 建议可改（assist 标注）；疗程三选一：长期服用(open) / 用完为止(stock，显示推算天数) / 自定义天数(closed)；
5. 健康信息"建议填入"勾选区（处方诊断/性别/年龄 → 勾选才写入）；患者信息与账号明显不一致 → "这是给谁用的药"提示；
6. 范围校验/相互作用结果区（分级色 + 文字 + 来源展示）；入口B 草稿显示标签提示（`labelNotice`）；
7. 确认/信息不符按钮 + 提交后跳转。

**完成标准**：对着 PRD §10.2 逐条自验有截图；`needsManual` 字段无法被预填值（集成测试或组件断言）；冲突清单不自动选择。

## T8. 录入页前端（`/intake/rx`、`/intake/drug`）

**做什么**（参照 demo `pages/Entry.tsx`）：

1. 两入口分页：拍摄/相册单张上传、各自拍摄引导文案（处方笺：平铺完整、覆盖 Rp 至处方完毕；药盒：正面清晰）、隐私提示（"图片可能包含个人健康信息"）；
2. 上传中状态（进度、阶段文案：层检测→识别→解析）；detect 结果反馈可纠正（"识别到处方笺"与所选入口不符 → 确认/切换，对应 409 处理）；
3. 不支持对象（散装药片）→ 明确不支持文案 + 安全提示；质量问题 → 具体重拍建议（反光/过暗/遮挡）；
4. 处方笺多草稿 → 草稿列表页逐个确认；AI 不可用 → 明确降级引导到手动建档。

**完成标准**：五个 golden case 场景在 UI 上全部可达且有正确反馈（本任务用 mock 管线响应验证 UI 分支）。

## T10. golden case E2E（Playwright）

**为什么需要回放机制**：管线依赖三个外部模型，真实调用慢、贵、结果不确定，CI 不能依赖。E2E 验证的是**接线**（上传→编排→草稿→确认页→事务落库）而非模型能力（模型能力靠录制时的人工审核与 M2 各步单测保证）。

**怎么做**

1. 建 `app/e2e/`：Playwright 配置 `webServer` 同时起 api(8787，测试库) + web(5173)，CI 独立 job；脚本 `pnpm test:e2e` 与单测分离；
2. **fixture 回放机制**（基于 T1 的 `AiClients` 注入接缝）：
   - 有 key 的本地环境对每个场景跑一遍真实管线，把模型逐步原始响应（层检测 / OCR / VLM 身份 / 兜底解析）录制为 `e2e/fixtures/<scenario>.json`；
   - 录制结果**人工审核一次**——这一遍就是 golden case 的 oracle；审核通过的 fixture 进 git，CI 与日常回归永远回放这批文件（编排、降级、事务、API 走全真代码，只冻结模型 I/O）；
   - 实现 `FixtureAiClients implements AiClients`：E2E 进程以 `AI_MODE=fixtures` env 启动 api，按请求携带的 `x-test-scenario` 头取对应场景响应包；换 prompt/换模型版本时重录并重审；
3. **五个 golden case 场景**（PRD §16.1，场景名即 `x-test-scenario` 值）：
   - `rx-normal` 合成处方笺端到端：草稿字段全对（药名/规格/用量/频次/途径/疗程/结束日期推算）→ 确认 → 药箱+计划生效；
   - `rx-spec-conflict` 规格冲突：库条目 0.2% vs 处方 0.1% → 确认页出现冲突提示且不自动选边；
   - `rx-redacted` 涂黑遮挡：被涂字段按缺失处理走人工补，无猜测预填；
   - `drug-box-labeled` 药盒（含贴标）：不产出任何用法用量草稿；出现"标签用法不自动抄录"提示；
   - `unsupported-loose-pills` 散装药片：明确"不支持"提示；
4. **断言三层**（不只看 UI）：
   - UI 断言：冲突清单可见、needsManual 输入框为空、标签提示出现、"不支持"文案、确认后跳转；
   - DB 断言：测试代码直连测试库验证确认事务落库（drugs/plans/sources/health_profiles 行存在、drafts.status=confirmed）；
   - **结构断言**（PRD 红线）：`drug-box-labeled` 的草稿 payload 中不存在任何用法用量字段；`rx-redacted` 的人工补字段值为空——防"预填猜测"与"标签抄录"比肉眼截图更可靠；
   - `unsupported-loose-pills` 额外断言 OCR 未被调用（fixture 客户端记录调用日志）；
5. 样张资产：合成处方笺 golden case 图 + 涂黑变体 + 药盒/散装图入 `app/fixtures/`（git 管理，与 T9 共用）；
6. **真实路径**：有 key 环境提供 `pnpm test:e2e:live` 跑真实管线（发布前/验收时手动跑，非回归手段）。

**完成标准**：五个 E2E 在 fixture 模式全绿且可在无 key 环境（CI）复现；结构断言与"OCR 未调用"断言生效（临时注入违规 fixture 能让对应测试失败——验证后移除）；README 更新 E2E 运行/录制说明。
