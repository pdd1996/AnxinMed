## 1. 结论：批准文号不是"药品身份"字段

- 批准文号是**注册许可标识**：同一药品不同规格/包装规格通常各有独立批号（本药说明书原文即写明
  「80mg规格：国药准字H20138001；240mg规格：国药准字H20138002」），再注册续期不改号，但技术转让、
  持有人/场地/工艺等注册变更可能换发；同一批号下还有 7片/14片/28片 等包装规格。
- 批号多印在包装**侧面/背面小字**，不是"拍药盒正面"能核对的字段；把它放在「药品身份」核对区，
  既让用户误以为是识别出来的，也可能张冠李戴（现场就是如此）。
- 因此：**批号不参与身份核对展示，也不作为唯一匹配依据**；身份核对只保留实物可核对项：
  药名 / 商品名 / 规格 / 剂型 / 厂家。

## 2. 数据现状（为什么会出现错号）

- 全库 `drug_master` **1588 行全部是 `crawled`**（reviewed = 0），来自说明书 PDF 自动抽取；
- 其中 **141 行登记了多个批准文号**、**262 行规格文本是"多个规格合并"形态**（含部分单规格复方误报，
  实现里用保守规则剔除）；典型如 `阿利沙坦酯片`：一行 `specification: "80mg，240mg"`、
  `approval_number` 只取第一个（80mg 的 H20138001），240mg 的批号只在 `approval_numbers` 数组里。
- 旧逻辑：规格按 token 重叠 → 该合并行被判 `unique` → 身份卡展示主批号 → 240mg 盒子被配了 80mg 的批号。

## 3. 决策（方案 B：选填 + 不阻塞 + 拍照优先）

1. **展示止血**：确认页「药品身份 / 药品库唯一匹配」块**不再展示批准文号**；
   「识别抄录值（供对照）」里仅当照片确实抄到批号时才显示（标「批准文号（照片抄录）」），
   不再输出「—」占位；候选卡片也不再展示批号。
2. **匹配止血**：`isMultiSpecEntry`（多批准文号 或 规格文本为多规格合并）的库条目**禁止判 unique**，
   降级为候选交用户按实物规格选择（说明文案透传到冲突清单）。
3. **选填输入（仅歧义场景）**：冲突清单出现「批准文号（选填）」输入框——只在包装上印了时填，
   用于在候选中**命中定位**（命中显示「批号命中（用户填写·未校验）」），
   **不做官方校验、不落库、不参与 confirmStatus 判定**；不填不影响主流程。
4. **选定后规格取值**：选中多规格合并条目时，写入用户档案的规格取**识别抄录值**
   （如 `240mg×7片`），不把合并规格 `80mg，240mg` 写进药箱。

## 5. 顺带修复（同次真机照片验证发现）

用真实药盒照片跑管线时发现：药盒正面印了英文剂型（`Allisartan Isoproxil Tablets`），VLM 把 form
抄成 `Tablets`，与库内中文「片」逐字比对 → 误报「剂型冲突」，把本次的多规格候选路径整个短路掉。
已在 `normalize.ts` 增加 `canonicalForm`（英文/别名 → 中文基形，如 Tablets→片、Eye drops→滴眼液、
Capsule→胶囊、Injection→注射液…），剂型比对先归一化再双向子串；真不一致（Tablets vs 胶囊）仍然拦截。
