## 二、两项反复讨论问题的论证存档

### 为什么不是 Next.js

Next.js 的不可替代价值是服务端渲染，服务于 SEO、公开内容页、首屏字节级优化——本项目一条不占（登录后使用的私人工具，无页面需要被索引）。且它与已定架构冲突：Hono 后端 + 静态 dist 单容器 vs Next 的 Node 服务器运行时与双服务端职责重叠。「为后面做打算」的正确形态是将来**另起独立营销小站**，不是给主应用换框架。老年用户首屏问题的对症解法是 PWA 缓存与大字号交互，不在框架层。

### 为什么不是 SQLite / MySQL

- SQLite：本项目中省不下实际成本（compose 下 PG 近零成本），却丢掉 JSONB/pgvector/zhparser 全部未来选项，且统计 SQL 的 `count(*) filter (where ...)` 等 PG 方言要重写，引入 dev/prod 方言漂移风险。SQLite 的正确场景是纯本地单机工具。
- MySQL：能力上可行，但 PG 在本项目用到的每一点上（JSON 字段、向量预留、全文预留）都 ≥ MySQL，且无 utf8mb4 字符集坑。已选 PG。

## 四、M1 实测结论（医嘱线 OCR · ADR #13）

> 注（2026-09-07）：本条目已被 **ADR #16（见 §五）** 取代——医嘱线 OCR 改用 qwen3.5-ocr 云端 VLM 转录。以下实测数据与结论为 PaddleOCR 时期存档，历史正文不改写；`tools/ocr-bench/` 保留作基准脚本存档。

> 实测脚本与样张：`tools/ocr-bench/`（`make_sample.py` 生成合成打印体处方笺 + ground truth；`bench_paddle.py` 跑 PaddleOCR 并出指标，结果落 `paddle-result.json`）。
> 样张说明：暂无真实脱敏处方笺，按任务书允许以**合成打印体处方笺**替代（含 2 条医嘱行：药名/规格/用法用量），ground truth 精确已知。

### 候选 A：PaddleOCR 自托管（PP-OCRv4，paddleocr 3.7 + paddlepaddle 3.3.1，CPU）

| 维度 | 实测结果 | 是否满足 |
|------|----------|----------|
| 医嘱行识别准确率（字符级，空白归一） | 1.0000（4/4 行完全一致） | ✅ |
| 全行识别准确率（字符级，空白归一） | 0.9722（11/12 行完全一致） | ✅ |
| 字符级置信度 | 提供（样本 0.97–1.0） | ✅ 硬要求 |
| 坐标（检测框） | 提供（每行 polygon） | ✅ 硬要求 |
| 端到端耗时（单张） | 初始化 ~10s；推理 ~69s（见注 1） | ⚠️ 本机不达标 |
| 部署负担 | 自托管（python / docker 镜像），无外部 SaaS 依赖 | 中 |
| 数据不出服务器 | 是（本地推理） | ✅ 加权项 |

- 注 1（耗时）：~69s/张 为**本机 Windows CPU、且为绕过 paddlepaddle 3.3.1 的 PIR/oneDNN 引擎 bug 而关闭 mkldnn**（`enable_mkldnn=False`）的测得值；关闭 oneDNN 使 CPU 推理显著变慢，属环境/workaround 产物而非模型本身。生产部署于 Linux 并启用 oneDNN（或引擎 bug 修复后）通常为 1–3s/张，**该值未在本机实测**，列为生产复测项。
- 注 2（引擎 bug）：paddlepaddle 3.3.1 Windows CPU 在 PIR+oneDNN 下抛 `NotImplementedError: ConvertPirAttribute2RuntimeAttribute … onednn_instruction.cc`；workaround 为 `enable_mkldnn=False`（见 bench 脚本注释）。

### 候选 B：阿里云高精 OCR（通用文字识别）

**未实测**。本次 `.env` 未提供阿里云 OCR key（亦不编造数据），故无准确率/置信度/坐标/耗时实测值。按其文档满足词级置信度 + 坐标，但缺实测支撑，不作为定案依据。

### 定案

定案 **PaddleOCR 自托管** 为医嘱线 OCR。理由：合成打印体处方笺上医嘱行字符准确率 100%、字符级置信度与坐标均满足 PRD 硬要求、数据不出服务器（ADR 加权项）。保留两条：

1. **耗时复测**：生产（Linux + oneDNN）部署后复测单张耗时；若不满足医嘱线 P95 ≤ 15s 预算，重议。
2. **阿里云补测**：提供 key 后补测候选 B；若其准确率/运维优势显著且可接受数据出服务器，按 #13 重议触发条件重开讨论。

`.env` 不含任何提交的 key（本次未新增 OCR/模型 key）。

## 五、ADR #16：医嘱线 OCR 改用 qwen3.5-ocr 云端 VLM 转录（2026-09-07）

### 背景（#13 重议触发条件实质命中）

ADR #13 定案 PaddleOCR 自托管时保留了两条重议通道（生产复测耗时不达标即重议）。事后盘点，触发条件已实质命中：

1. **本机耗时不可用**：Windows CPU 实测 ~69s/张（docs/09 §T5.1；为绕过 paddlepaddle 3.3.1 PIR/oneDNN bug 关闭 mkldnn 的 workaround 产物），远超医嘱线 P95 ≤ 15s 预算；
2. **生产复测从未完成**：Linux + oneDNN 部署复测始终未执行——自托管侧车（python / docker 镜像）从未进入 docker-compose，生产形态自始至终不存在；
3. **云端质量已验证**：demo 已用 qwen3.5-ocr 调用同一形态端点（OpenAI 兼容 chat/completions），验证了处方笺转录质量与行序保持。

### 决策

医嘱线 OCR 改用 **qwen3.5-ocr 云端 VLM 转录**，取代 #13 的 PaddleOCR 自托管：

- **客户端**：`app/packages/api/src/lib/ai/ocr.ts`，`POST {OCR_BASE_URL}/chat/completions`（OpenAI 兼容多模态），prompt 要求「请逐行转录这张图片中的全部文字，保持原始行顺序，不要添加任何注释、翻译或总结。」；
- **诚实契约**：`OcrResult = { lines: string[] }`——qwen3.5-ocr 只返回行级纯文本（无字符级置信度/坐标），契约如实反映引擎能力，不伪造字段；
- **超时与重试**：OCR 调用 60s 超时 + 重试退避 500ms，仍失败抛 `AIUnavailableError`（录入转 `OCR_FAILED` 降级草稿，不 5xx）；
- **环境变量三件套**：`OCR_BASE_URL` / `OCR_API_KEY` / `OCR_MODEL`（默认 `qwen3.5-ocr`），取代原 `OCR_PROVIDER` 占位。

### 代价与取舍

- **字符级置信度与坐标退役**：qwen3.5-ocr 不提供该能力，「低置信字符标红」（PRD §7.2.5）与「正文裁剪图几何对照」（PRD §12.2）随切换移除，确认页退化为「整图 + 文字原文对照」（PRD V2.2，见 PRD §0.2）；
- **L0 版面裁剪改为行序裁剪**：以 Rp / 处方完毕锚点行界定正文行区间，前记/后记按行整块丢弃——隐私四层与守门规则不降级（前记/后记仍整块丢弃，OCR 原图内存即用即弃、不落盘，落库仅白名单字段，L3 红线不变）；
- **数据出服务器口径变化**：处方原图需经加密通道发送给云端 VLM 端点（#13 的「数据不出服务器」加权项在本条目上让位于可用性：69s 不可用 vs 云端秒级）；缓解：原图仅本次转录使用、即用即弃，落库仍仅白名单字段，零泄漏断言继续覆盖。

### 保留项

- qwen3.5-ocr 云端单张延迟 live 复测（对齐 docs/09 §T5.1 遗留项的 P95 复测口径）；
- `tools/ocr-bench/` 不动，作为 #13 PaddleOCR 实测存档保留。
