```
└───────┬─────────────────────────┬─────────────────┘

│ postgres:16    │   │ 外部 AI 服务（Key 只在后端 .env）│

└────────────────┘   │ · Baichuan-M3-Plus（咨询/摘要） │
                     └───────────────────────────────┘
```

要点：

- **单页应用 + 单 API 服务**：前端纯静态产物由 Hono 托管，无 Node 模板层、无 SSR；
- **业务复杂度全部在 service 层**，且尽量实现为可单测的纯函数（管线、脱敏、规则）；
- **数据库与外部模型之间有硬边界**：一切模型输出必须过 zod `safeParse` + 各自的守门规则才能接近数据库。

## 4. 数据模型（9 张表）

**用户域**（全部带 `userId`，从第一天贯通多用户边界）：

| 表 | 回答的问题 | 关键字段 |
|----|-----------|---------|
| `users` | 谁在用 | Better Auth 兼容形态；MVP seed：1 名演示患者 + 8 名 Mock 患者 |
| `drugs` 药箱 | 我有什么药 | 身份快照（通用名/商品名/规格/剂型/厂家）、`confirmStatus` 三档（ocr_matched / transcribed / manual）、库存 `{value, unit}`、开封日期 |
| `plans` 计划 | 怎么吃、吃多久 | 用量、频次、时间点[]、周期形态（开放/封闭）、起止、状态、`sourceId`/`itemId` 反查、四类标注（JSON：字段→抄录/辅助/推算/默认） |
| `records` 记录 | 实际吃了没 | 计划、预定时间、状态（taken/later/skipped）、实际操作时间 |
| `sources` 来源 | 档案从哪来 | 类型（处方/药盒/手动）、正文裁剪图引用、白名单字段（JSON）、处方号、确认留痕（时间/方式/字段快照） |
| `health_profiles` 健康信息 | 用户背景 | 字段级来源标注（用户自述 / 处方抄录·已确认） |

**资产域**（Mock，与代码分离，write-once）：

| 表 | 内容 |
|----|------|
| `drug_master` 药品身份库 | schema 对齐 NMPA（批准文号/厂家/规格/剂型），识药匹配对象 |
| `package_inserts` 说明书库 | 身份组 + 内容组（标准分段结构化）+ 来源三件套（source/version/sourceUrl） |
| `interaction_rules` 相互作用库 | `{drugIds[], level 四级枚举, note, source}`，条目禁止模型生成 |

**核心不变式**：药品主数据库 ≠ 用户药箱；医嘱只抄录不生成（用量/频次/疗程只能来自确认的原文或用户自填）；续方 = 新计划行。

## 5. API 设计

```
# 健康
GET  /api/health

# 拍照录入
POST /api/intake/detect            # 层检测（入口校验，VLM）
POST /api/intake/prescription      # 入口A：层检测+医嘱线+身份线 → 草稿
POST /api/intake/drug              # 入口B：身份线 → 建档草稿（贴标药盒不抄录标签，检测到标签时返回提示）
GET  /api/drafts/:id               # 草稿详情（原文对照数据）
POST /api/drafts/:id/confirm       # 确认生效：事务写 drugs+plans+sources+health
POST /api/drafts/:id/reject        # 信息不符 → 留痕

# 药箱 / 计划 / 任务
GET/POST /api/drugs                # 手动建档走 POST（confirmStatus=manual）
GET/PATCH/DELETE /api/drugs/:id
GET/POST /api/plans                # 变更后自动重跑相互作用检查
PATCH/DELETE /api/plans/:id
GET  /api/tasks/today
POST /api/records/:id/take|later|skip

# AI
POST /api/consult                  # 键盘取数+百川+守门，返回 citations+riskLevel
GET  /api/insight/patients         # 医生端（M3 对齐新表）
POST /api/insight/summary
```

约定：入参全部 zValidator 校验；错误统一 `{ ok: false, code, message }`；`resolveUser` 中间件注入当前用户（MVP 返回 seed 演示用户，P1 换 Better Auth session）。

## 6. 医嘱线管线（技术核心，M2）

每一步都是独立纯函数，单测覆盖，串行编排：

```
① detectLayers(image)        Qwen3-VL → zod 枚举 {处方层|医院标签层|药盒原装层|说明书层|不支持}
                             （医院标签层仅用于入口B的建档提示，不进入医嘱线——PRD V2.1 §0.1）
② runOcr(image)              OCR 引擎（M1 实测定案）→ 字符/置信度/坐标（仅处方层触发）
③ cropBody(ocrResult)        锚点定位（Rp / 临床诊断 / 处方完毕）→ 正文裁剪；前记后记整块丢弃
④ parseWhitelist(text)       正则模板解析（"每次X/每日X次/共X天"）→ 闭合 schema（.strict()）
⑤ sanitizeScan(fields)       L2 兜底：手机号/身份证/地址模式 → [已脱敏] + 审计计数
⑥ verifyBacklink(fields,text) 回链校验：模型兜底解析的每个值必须在裁剪文本中逐字可寻
⑦ buildDraft(...)            草稿汇合：档案草稿+计划草稿+健康信息建议+相互作用+范围校验
```

失败方向统一"宁可失败"：任何一步不过 → 降级到原文人工补 / 手动建档，不预填猜测。

**身份线**（并行于 ③–⑥）：VLM 提取身份字段 → `drug_master` 三项严格匹配（药名+规格+剂型）→ 唯一匹配才通过；冲突/多候选进草稿冲突清单，不自动裁决。

**确认生效事务**（POST /api/drafts/:id/confirm）：单事务原子写 `drugs` + `plans` + `sources` + `health_profiles`（勾选项）+ 确认留痕。

## 7. 安全体系

| 机制 | 实现 |
|------|------|
| 脱敏 L0 版面裁剪 | 几何裁剪，前记后记不进入后续任何环节 |
| 脱敏 L1 白名单 | zod `.strict()` 闭合 schema，schema 外无字段 |
| 脱敏 L2 黑名单兜底 | 模式匹配纯函数，命中替换 + 审计（只记类型与次数） |
| 脱敏 L3 出口约束 | OCR 原文内存即用即弃；发第三方仅白名单字段；日志不落原文 |
| 风险分级 L4/L3/L2/L1 | 咨询与洞察共用守门；L2 剂量过滤（stripDosageAdvice） |
| 零泄漏断言 | CI 测试：任何持久化输出/日志/第三方请求中出现身份模式 = 0 |
| Key 管理 | 只在后端 `.env`，` .gitignore` 忽略 |

## 8. 前端设计

**路由**：`/`（今日任务）· `/box`（药箱）· `/intake/rx`（拍处方笺）· `/intake/drug`（拍药品）· `/drafts/:id`（确认页）· `/consult` · `/profile` · `/settings`；`/doctor/insight` 独立分支不进底部导航。

**状态分治**：服务端数据全走 TanStack Query（药箱/任务/计划/咨询），`useOptimistic` 做服药打勾；UI 状态（当前 Tab、提醒弹窗队列、语音面板、字号档）走 zustand。

**老年向设计令牌**（M1 建立，先于业务页面）：基础字号 16–18px、触控目标 ≥44px、风险语义色（L4 红 / L3 橙 / L2 蓝 / L1 绿）、高对比文字、字号两档切换；语义提示图标 + 文字并用，不单靠颜色。

**语音**：浏览器 SpeechRecognition / speechSynthesis，失败即降级文字与按钮（不阻塞主流程）。

## 10. 部署与运维

## 11. 非功能目标

- 医嘱线端到端（上传→草稿）P95 ≤ 15s；
- 模型不可用不影响本地核心功能；
- 日志不暴露非必要敏感信息；
- 无障碍：键盘可达、焦点管理（Radix）、语义色 + 文字冗余。

## 13. 风险与对策（技术侧）

| 风险 | 对策 |
|------|------|
| OCR 选型不达预期（置信度/坐标不满足） | M1 提前实测，两家候选 + 备选 PaddleOCR 云端托管 |
| 处方写法多样，正则覆盖不足 | 原文人工补为主、模型兜底必须过回链校验、golden case 持续回归 |
| 层检测误判 | 入口校验不静默改道，用户可纠正；金样例回归 |

## 14. 与实现的偏差记录（M1–M3 收尾，任务书 T6.3）

> 记录技术方案定稿后、实现过程中的有意偏差；真相以代码为准，本节为对照索引。

**接口合并 / 新增**

- 服药记录：demo 的 take/later/skip 三路由 → 合并为单一 `POST /api/records`（`{planId,date,time,status}`），同 (计划,日期,时间点) 重复 → **409**（比 demo 覆盖更新更严格，M1-T7）。
- 记录查询：新增 `GET /api/records?from&to`（M3-T6，PRD §7.4「按日周月查询与导出」），返回条目（联 plans→drugs 取药名）+ 状态聚合（PG `count(*) filter`）。
- 录入：`POST /api/intake/{detect,prescription,drug}`；草稿：`GET /api/drafts/:id` + `POST /api/drafts/:id/{confirm,reject}`（confirm 单事务原子写 sources+drugs+plans+health_profiles+drafts.status，M2-T6/T7）。
- 咨询：单一 `POST /api/consult`（守门 L1–L4 + manual 档门禁 + 医疗搜索默认关，全在 service 编排，M3-T1）；医生端 `GET /api/insight/patients` + `POST /api/insight/summary`（M3-T3）。

**表结构微调**（原九表基础上）

- 新增 `drafts`（M2-T6）：草稿载荷，status `pending→confirmed/rejected`，payload 存脱敏后白名单 + 裁剪几何（不存原图，L3 红线）。
- 新增 `consult_logs` + `risk_events`（M3-T1）：咨询留痕 + L4/L3/manual-gate 风险事件，供 M3-T3 医生端只读消费。迁移 `0003_stormy_thunderbolt_ross.sql`。

**AI 客户端层**（方案「后端代理转发模型请求」的具体化）

- 统一 `AiClients` 注入接缝（`lib/ai/registry.ts` getAiClients/setAiClients）：生产 `createAiClients()`（qwen/ocr/baichuan）、单测 mock、E2E `FixtureAiClients` 回放（`AI_MODE=fixtures`，按 `x-test-scenario` 头隔离）；管线 run.ts 不感知差异。
- `callJson` 超时 30s + 重试 1 次（4xx 除 429 不重试）+ 失败抛 `AIUnavailableError`（语义化，上层转降级/503，绝不静默）。
- OCR：PaddleOCR **自托管**，Node 经 HTTP 调用（`OCR_BASE_URL`），非进程内跑 Paddle（ADR#13）。

**前端**

- 状态分治如方案；服药打勾的 `useOptimistic` 实际以 `useMutation` 的 `onMutate` 乐观更新 + `onError` 回滚 + `onSettled` 失效实现（等效，M1-T9）。
- 语音（M3-T4，demo 无、方案 §8 已列）：Web Speech API（`SpeechRecognition` 录入 + `speechSynthesis` 播报），能力探测 + 不支持降级置灰，等价手动路径保留。

**性能 / 运维**
