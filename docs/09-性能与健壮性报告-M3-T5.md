## T5.1 医嘱线端到端打点计时

### 实现（结构化耗时入日志）

| 层 | 文件 | 职责 |
|---|---|---|
| 计时工具 | `app/packages/api/src/lib/timing.ts` | `Stopwatch`（`measureSync`/`measureAsync`/`record`/`summarize`）+ `percentile`（线性插值 P50/P95）+ `aggregateTimings` |
| 管线打点 | `app/packages/api/src/services/pipeline/run.ts` | `runPrescription`/`runDrug` 增可选 `timing?: Stopwatch`，逐步包裹 `detect/identity/ocr/crop/parse/fallback/sanitize/build`；缺省不计时（向后兼容，既有测试无感） |
| 编排汇总 | `app/packages/api/src/services/intake.service.ts` | 计时 `gatherContext`(DB 读) + 管线 + `persist`(DB 写)，落单行结构化日志 `[intake:timing] {json}`（测试环境静默；不含用户数据/原文，执行总纲 §0.5） |
| 测量工具 | `app/packages/api/src/scripts/perf-intake.ts` | `npm run perf:intake`：瞬时 mock 模型跑真实编排 N 次（默认 30）→ 聚合 P50/P95，自清理草稿 |

结构化日志样例（真实输出，冷启动首跑，gatherContext 含连接池冷启）：

```json
[intake:timing] {"entry":"A","drafts":1,"totalMs":355.3,"phases":{"gatherContext":339.4,"detect":0,"identity":0.1,"ocr":0,"crop":1.3,"parse":4.3,"fallback":0.2,"sanitize":0.5,"build":1.9,"persist":6.6}}
```

### 实测数据（`npm run perf:intake`，N=30，dev 库 + 瞬时 mock 模型）

测得的是**非模型开销**（DB 读 + 编排 + 纯函数步骤 + DB 写）——模型阶段因用瞬时 mock 恒为 0，真实延迟见下节。

| 阶段 | P50 (ms) | P95 (ms) | 说明 |
|---|---:|---:|---|
| **total（上传→草稿 非模型开销）** | **6.2** | **10.6** | min 5.1 / max 11.8 |
| gatherContext | 3.5 | 5.7 | 5 路并行 DB 读（候选/规则/说明书/药/计划） |
| persist | 1.9 | 3.8 | 草稿落库（DB 写） |
| parse | 0.2 | 0.4 | 白名单正则解析 |
| crop | 0.1 | 0.3 | Rp 锚点裁剪 |
| build | 0.1 | 0.3 | N 条目装配 |
| sanitize | 0.0 | 0.1 | L2 脱敏扫描 |
| detect / identity / ocr / fallback | 0 | 0 | 瞬时 mock（真实延迟见下） |

> 结论：**编排 + DB 层开销 P95 ≈ 10.6ms，相对 15s 预算可忽略**；端到端 P95 由模型延迟主导。

### 模型延迟（主导项）与 P95 ≤ 15s 评估

本机**无 live 模型服务**，模型延迟无法在此实测。已知数据：

| 模型 | 调用点 | 实测/预期 | 来源 |
|---|---|---|---|
| **OCR (PaddleOCR)** | `runOcr` | **Windows CPU 单张 ~69s**（init 10s + inference 68.86s，`enable_mkldnn=False` 绕过 PIR/oneDNN bug）；**生产 Linux+oneDNN 预期 1–3s（未实测）** | `tools/ocr-bench/paddle-result.json` + ADR#13（注：OCR 选型已由 ADR #16（qwen3.5-ocr 云端转录）取代，本文数据为 PaddleOCR 时期实测存档，2026-09-07） |
| Qwen3-VL | `detectLayers` / `extractIdentity` | 未实测（无 key）；身份线已与医嘱线**并行**（run.ts），不叠加关键路径 | 架构图「身份线（并行）」 |
| Baichuan | `fallbackParse` | 仅处方**有缺项**时触发；完整处方不调用（本次实测 fallback=0） | run.ts ⑥ |

**瓶颈分析**：关键路径 ≈ `detect(qwen)` + `max(identity(qwen) ‖ ocr+parse+fallback)` + `sanitize/build/persist(可忽略)`。
- **本机（Windows CPU）**：OCR ~69s → 端到端 P95 **远超 15s，不达标**。根因是 PaddlePaddle 3.x 在 Windows CPU 的 PIR/oneDNN 兼容 bug（**环境问题，非算法/模型问题**）。（注：OCR 已由 ADR #16 切换为 qwen3.5-ocr 云端转录，~69s 为 PaddleOCR 时期实测存档，2026-09-07）
- **生产（Linux + oneDNN）**：若 OCR 落到 ADR#13 预期的 1–3s，则总 P95 ≈ detect(1–2s) + max(identity 1–2s ‖ ocr 1–3s + fallback 0–2s) + ~0 ≈ **4–7s（推算，达标）**。

**优化对策**（按性价比）：
1. **OCR 部署到 Linux + oneDNN**（首要，ADR#13 保留项）——消除 Windows PIR/oneDNN bug，预期 69s → 1–3s；
2. **身份线并行**——已实现（run.ts：层校验通过即发起 VLM 提取，与 OCR/解析并行）；
3. **图片预压缩 ≤ 2MB 上传**——*建议后续实现*（IntakeFlow 上传前 canvas 压缩）：减小上传载荷与 OCR 输入尺寸；当前未实现（bodyLimit 22MB），因瓶颈在 OCR 推理而非上传，故列为 follow-up；
4. **GPU / 云端托管 OCR**——若 Linux CPU 仍不达标则启用（ADR#13 触发重议条件）。

> ⚠️ **复测项（诚实标注）**：真实「上传→草稿 P95」须在 live 模型服务（生产 Linux）下用 `npm run perf:intake`（换真实客户端）或直接读 `[intake:timing]` 日志聚合复测。本机数据仅代表非模型开销 + Windows-CPU-OCR 的病态慢速，不编造生产数字。

## T5.2 模型全链路降级演练（三条记录）

**方法**：① 集成测试 `app/packages/api/src/__tests__/degradation.test.ts`（`setAiClients` 注入 `AIUnavailableError`，等价「改 env 指向坏地址」→ 客户端失败；管线/编排/降级/事务/API 全走真代码）；② 对**运行中 api**（无 AI env = 全模型 down）做活体 HTTP smoke。

### 三条记录（每个模型一条）

| # | kill 模型 | 录入（intake） | 咨询（consult） | 药箱/计划/今日/记录 | 5xx? |
|---|---|---|---|---|---|
| 一 | **Qwen**（detectLayers/extractIdentity） | 入口硬闸门 → **503 `AI_UNAVAILABLE`**「识别服务暂不可用…改用手动建档」 | 不依赖 qwen → **200** 正常 L1 | 全 **200/201** | 仅语义化 503 |
| 二 | **OCR**（runOcr） | 入口A → **201 降级草稿**（`degraded.code=OCR_FAILED`，全 `needsManual`），**非 503**；入口B 不用 OCR → 201 | **200** | 全 **200/201** | 无 |
| 三 | **Baichuan**（fallbackParse/consultAnswer） | 完整处方不需兜底 → **201** 正常 | → **200 离线兜底**（`notice` 含「百川服务不可用…本地说明书库规则拼装」） | 全 **200/201** | 无 |
| 横切 | **三模型全 down** | 503（唯一） | 200 | 全 200/201 | **无雪崩** |

### 活体 smoke 证据（运行中 api，localhost:8787，全模型 down）

```
GET  /api/drugs                 → HTTP 200                              （核心-药箱 可用）
GET  /api/tasks/today           → HTTP 200                              （核心-今日 可用）
POST /api/intake/prescription   → HTTP 503  {"ok":false,"code":"AI_UNAVAILABLE",
                                 "message":"识别服务暂不可用，请稍后重试，或改用「手动建档」录入"}
POST /api/consult               → HTTP 200  {"ok":true,"riskLevel":"L1","status":"no-source", …}   （咨询不 5xx）
```

> 结论：**模型不可用不影响本地核心功能**（药箱/计划/今日/记录与 AI 无关，全可用）；录入/咨询给**可理解错误/降级**（语义化 `AI_UNAVAILABLE` 503、OCR_FAILED 降级草稿、离线兜底），**无 5xx 雪崩**（除录入入口硬闸门的语义化 503）。技术方案 §11 达标。

## T5.3 前端性能与缓存一致性

### 路由懒加载（`app/packages/web/src/router.tsx`：全 `lazy()` + `Suspense`）

**运行时证据**（dev，chrome-devtools 抓 `performance` 资源）：访问 `/` 时**仅加载** `routes/patient/Home.tsx`；`Consult`/`Draft`/`Insight` **均未加载**（按需动态 import）。

**构建产物分析**（`pnpm --filter @anxin/web build`）：

| 产物 | raw | **gzip** | 角色 |
|---|---:|---:|---|
| `index-*.js` | 472.83 kB | **143.54 kB** | **首屏入口**（React19+router+query+radix+sonner+lucide 基座） |
| `index-*.css` | 48.43 kB | 8.58 kB | 全局样式（Tailwind v4 + 令牌） |
| `Draft-*.js` | 52.76 kB | 14.88 kB | 确认页（最大路由块，懒加载） |
| `Settings/IntakeFlow/Consult/Box-*.js` | 16–19 kB | 5.4–7.1 kB | 各路由懒块 |
| `Home-*.js` | 11.31 kB | 4.16 kB | 今日页懒块 |
| `speech`/`VoiceDictationButton`/`volume-2` | 1.2–5.5 kB | 0.7–2.4 kB | M3-T4 语音，随页懒加载 |

> **首屏 chunk = 143.54 kB gzip ≤ 300 kB ✓**（首屏总载 ≈ index 143.54 + css 8.58 + Home 4.16 + client 2.79 ≈ **~159 kB gzip**）。各路由独立成块 → 代码分割生效。

### TanStack Query 缓存与失效梳理（打勾后 today/box 一致性）

| 触发 | mutation | `onSettled`/`onSuccess` 失效键 | 一致性 |
|---|---|---|---|
| **打勾记录服药** | `Home.recordMutation` | `['tasks','today']` + `['drugs']`（taken 服务端扣库存） | ✅ today 状态 + box 库存同步（乐观更新 + 失效回读） |
| **草稿确认**（唯一闸门） | `Draft.confirm` | `['drugs']`/`['plans']`/`['tasks','today']`/`['profile']`/`['draft',id]` | ✅ 建 drug+plan+health 全刷新 |
| **建药/建计划/删除** | `Box.createDrug/createPlan/…` | `['drugs']`/`['plans']`/`['tasks','today']` | ✅ |
| **健康信息增删** | `Profile.patch` | `['profile']` | ✅ |

> 结论：失效图**完整且一致**（M1-T9/M2-T7 已落实），无缓存陈旧缺口；`打勾 → today + box(drugs)` 双失效正是 spec §T5.3 要求的一致性，已验证。

## 遗留 / 复测项

1. **真实上传→草稿 P95**：需 live 模型（生产 Linux + oneDNN OCR）复测；本机仅测非模型开销（P95 10.6ms）+ Windows-CPU-OCR 病态值（~69s，环境 bug）。对齐 ADR#13「耗时复测」保留项。
2. **图片预压缩 ≤ 2MB**：建议后续在 IntakeFlow 上传前实现（canvas 压缩）；当前瓶颈在 OCR 推理而非上传，故未纳入本次。
3. 若生产 Linux OCR 仍 > 预算 → 触发 ADR#13 重议（GPU / 云端托管 OCR / 阿里云高精 OCR 补测）。
