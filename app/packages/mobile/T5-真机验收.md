### 预检查出的缺陷：系统深色下 app 不翻转（§2 第 6 条不通过）

**现象（硬证据）**：`ui_night_mode=2`、`dumpsys uimode` = `mNightMode=2 (yes)`，且 `dumpsys activity top` 里本 app 的 `mLastReportedMergedConfiguration` **带 `night` 标记**（`... 420dpi nrml long port night ...`）——原生侧确实在深色；此时 release 包**运行中**（`emu-t5a-13/14/15`）与**冷启动**（force-stop 后重开，`emu-t5a-16`）都是全白底黑字。

**已排除**：`app.json:9` 的 `userInterfaceStyle` 本就是 `"automatic"`；`android/app/src/main/res/values/styles.xml:2` 的父主题是 `Theme.AppCompat.DayNight.NoActionBar`，`res/values-night/` 存在，清单 `configChanges` 含 `uiMode`；`src/` 里没有任何手动设 `colorScheme` 的代码。所以不是「Activity 被钉在浅色」。

**我先后判错两次，都记下来免得下次再踩**：
1. 第一次说「`.dark:root` 不匹配 `isRootDarkClassSelector`，是死代码」——不成立。`normalize-selectors.js:344-359` 另有 `isRootDarkVariableSelector`，形状正是 `class(dark)+pseudo(:root)`，**当 `options.darkMode.type === "class"` 时它会编译成 `rootVariables/dark`**。
2. 第二次说「深色段在编译期就没进包」——也不成立，而且错在取证方法：我拿 `#0a0a0a`/`#26262a` 去搜，那是**心算错的十六进制**（`hsl(240 10% 3.9%)` 实际是 `#09090b`）。按正确值搜，改前的包里 `#09090b`/`#27272a`/`#a1a1aa`/`#d4d4d8` **各 1 处，全都在**。⚠️ 更一般的一条坑：**Hermes 的串表是排序去重的公共池，「某个色值在不在包里」证明不了它被编成了什么形状**——我第一次拿这个当判据，方向就是错的。

**仍未证到的那一环**：`isRootDarkVariableSelector` 要的 `options.darkMode` 是 **metro 侧 `withNativeWind(config, {...})` 传进去的选项**（`metro.config.js:60` 只传了 `input` 与 `inlineRem`），tailwind.config 的 `darkMode:["class"]` 会不会流到这里，我没证。若没流到，`.dark:root` 就落到「普通 class 选择器」分支，运行时要求祖先挂 `dark` 类——而 RN 没有 `documentElement`，没人挂，**表现正好就是现在看到的：值在包里，但永不生效**。

**已做的改动 → 已在模拟器验证通过（2026-09-30 夜，新包 `73,185,477B / 22:10`，`BUILD SUCCESSFUL in 2m 11s`）**：① `src/global.css` 的深色段改成 `@media (prefers-color-scheme: dark) { :root {…} }`——这条分支（`isRootVariableSelector` + `isDarkModeMediaQuery`）**不依赖 `darkMode` 选项**，运行时由 `runtime/native/appearance-observables.js:44-50` 的 `colorScheme.get()` 选档；② `tailwind.config.js` 去掉 `darkMode:["class"]` 与 `safelist:["dark"]`（web 靠 html 挂 `.dark` 类，RN 没有挂载点）。验证结果：深色下整页翻黑、tab 图标与文字（`useUnstableNativeVariable("--foreground")` 一族）跟着翻、无黑压黑（`emu-t5a-19/20`）；**运行中直接切系统深浅色即时翻转，不必重启**（`emu-t5a-22` 是运行中切回浅色的图，与修复前的浅色同形、无回归）；两档字号在深色下都可读。

**单变量判别（做了一半，说清边界）**：只把 `darkMode:["class"]` + `safelist:["dark"]` 加回去、CSS 保持 `@media`，重新 `expo export` 比产物哈希 → **A(`ecb2d017…`) ≠ B(`df5b0507…`)**，即该配置确实改变编译产物（改的是 `dark:` 变体的形状），所以两处都保留。**没做**第三组「只回退 CSS 到 `.dark:root`、保持无 darkMode」，因此**不下「@media 是翻转的必要条件」这种死结论**——那要各出一包看屏幕才能归因，代价是一次 2 分钟的构建 ×2。

### 顺带查出并修掉的第二个缺陷：`settings.tsx` 用原生 `Text`，颜色类整个丢失

深色一翻过来，字号切换控件就露馅了：选中态是**黑字压黑底**（用户实拍）。根因与深色无关——`src/app/(patient)/settings.tsx:1` 的 `Text` 是从 `react-native` 直接 import 的，而 `TabsTrigger` 下发文字颜色靠的是 `ui/text` 的 `TextClassContext`（`tabs.tsx:35-40` 把 `text-foreground dark:text-muted-foreground` 放进 context，只有 `ui/text` 的 `Text` 会 `useContext` 取用，见 `text.tsx` 末尾的 `Text` 实现）。用原生 `Text` 就接不上，**文字颜色退回平台默认黑色**；浅色档下黑字压白底看着正常，所以 T4 到 T5-a 一路截图都没暴露。改成从 `@/components/ui/text` 引 `Text`（它自带 `text-foreground` 基类，即使没有 context 也有颜色）。**同类漏网已扫**：`src/` 里靠 `TextClassContext` 下发样式的只有 `ui/{badge,button,card,tabs}.tsx` 四个，业务页里把裸 `Text` 当 children 塞进去的**只有这一处**（其余 `<Button>` / `<Badge>` 没有裸 Text 子节点）。

**影响面**：不只 T5-a，T4 那四页与后续 T5-b～T5-e 全部适用（05d §7 第 5 条「mobile 缺 `--risk-l1..l4`」是同一片文件的同一个照搬问题）。归 **T5-f 前置**。

### 修 §7-6 时踩到的一条真坑：本仓库的 drizzle-orm **不导出 `coalesce`**

### 预检查出的缺陷：深色下字号选择器「选中那一格」文字黑压黑（已修，随 22:44 版复验）

**现象**：深色下两档选择器里，被选中的那格文字是黑的、底也接近黑，读不出来；浅色下完全正常。**跟 `selected` 状态走，不跟标签走**——切到「标准」，黑字就跟着跑到「标准」格（`t5e-pre-13` vs `t5e-pre-16` 两张互证）。

**根因两条，都有取证**：

1. `src/components/ui/tabs.tsx` 的选中态写的是 `bg-background dark:border-foreground/10 dark:bg-input/30`。按 05d §7-7 那条「令牌色带 `/alpha` 修饰符在 mobile 整条静默丢失」——我用 README 的探针法实测确认：`npx tailwindcss -i src/global.css --content <只含这几个类的探针>` 产出的 `out.css` 里**只有** `.dark\:text-foreground` 与 `.dark\:text-muted-foreground` 两条，`dark:bg-input`、`dark:border-foreground` **零命中**。于是深色下选中底只剩 `bg-background`＝与页面同色，选中态本来就快看不出来。
2. 更致命的一条：`settings.tsx` 的 `Text` **又从 `@/components/ui/text` 退回 `react-native` 直引**——这正是 09-30 深夜 commit `7b35934` 修过的老问题，T5-e 重写本页时退回了。原生 `Text` 接不到 `TabsTrigger` 经 `TextClassContext` 下发的颜色，落回平台默认黑。

**修法**（两片，都不写死色号）：`ui/tabs.tsx` 选中态改**实色** `bg-primary`，并把 `TextClassContext` 里的颜色类全部摘掉（只留 `text-sm font-medium`）；`settings.tsx` 换回 `ui/text` 的 `Text`，标签按 `active` 显式给**一条**颜色类（`text-primary-foreground` / `text-secondary-foreground`）。**为什么强调「一条」**：同一个元素挂两条同属性颜色类时，RN 侧谁赢由**生成 CSS 的先后**决定，不按 class 书写顺序——这次探针里 `text-foreground` 就排在 `text-muted-foreground` 前面，与 web 直觉相反。

**复验**（22:44 版，深/浅 × 标准/大字四格）：`fix-01`（浅·选中标准＝黑底白字）/ `fix-02`（深·选中标准＝白底黑字）/ `fix-03`（深·选中大字，大字档下同样可读）/ `fix-04`（回到标准+浅色，与 `fix-01` md5 相同）。运行中切深浅色即时生效，没有回归 09-30 那条。

**差异登记（§6 第 17 条要的「刻意不同」）**：选中档由 web 的「灰底列表 + 白底 pill」改成「**实色 `primary` 反色 pill**」（浅=黑底白字 / 深=白底黑字）。理由：mobile 拿不到 `/alpha` 与 `dark:` 的可靠组合，而反色对比对老年用户更强。**这条对以后所有用 `ui/tabs` 的页面生效**（目前只有设置页）。

### 最重的一条：所有 Dialog 在安卓上渲染为 `null`（已修）

**现象（硬证据）**：装 10-01 22:44 那版，模拟器药箱页点「手动建档」「编辑计划」——屏幕不动（`t5f-kb-03/04/05` 三张与 `t5f-kb-02` 同形，`uiautomator dump` 151 个节点里没有任何弹窗节点）；**同一屏点「拍照录入」正常 push 到录入屏**（`t5f-kb-06`）→ 触屏事件到得了 RN 的 `Pressable`，问题在弹窗自身。

**根因**：`ui/dialog.tsx:15` 的内容走 `@rn-primitives/dialog` 的 `Portal`，而 `@rn-primitives/portal` 的 `Portal` 只做一件事——把 children 写进一张 zustand 挂载表，自己 `return null`（`app/node_modules/@rn-primitives/portal/dist/index.mjs:34-48`）；真正把它渲染出来的是 `<PortalHost />`（同文件 `:29-33`）。全仓 `packages/mobile/src` 搜 `PortalHost` **零命中** → 有人写、没人读 → 任何原生平台上弹窗都是空的。`dialog.tsx:19` 已经把 `FullWindowOverlay` 在非 iOS 换成了 `Fragment`（所以不是那个坑），漏的是 host。

**为什么一路没被发现**：§2.6 风险 1 早就写了「Dialog Portal + `NativeOnlyAnimatedView` 首次使用，要确认能否弹出」；但 T5-b～T5-e 四片全没装机，§2.10 的模拟器预检走的是五 tab / 字号 / 深色，**一次都没点开过任何弹窗**。教训：**预检清单必须包含「每个新引入的交互原语至少真按一次」**，只看静态屏等于没验。

**修法**：`src/app/_layout.tsx` 在 `<Toaster />` 之后挂 `<PortalHost />`。`@rn-primitives/portal@^1.5.3` 本就是 `packages/mobile/package.json:13` 的显式依赖（vendored 的 react-native-reusables 带的），**不装新东西、不 prebuild、不动原生工程**。

**影响面**：提醒弹窗、确认记录、删药二次确认、计划弹窗、手动建档、健康信息编辑——**§2.6/§2.7/§2.9 的真机条目几乎每条都卡在这一步之前**。装机后第一件事就是逐个点开。

### 第二条：错误卡与提示色写死在 Tailwind 调色板，深色下不翻（已修，§6 第 16 条）

**根因**：T4/T5-b/T5-c 时期的错误卡一律写 `border-red-300 bg-red-50 text-red-700/800`、告警写 `text-amber-800/900`、成功写 `text-green-700`。这些是**固定十六进制**，不走 `global.css` 的令牌，所以 `@media (prefers-color-scheme: dark)` 翻不动它们——深色下会出现「近黑页面上贴一块 #fef2f2 白卡」，而裸文字更糟：`text-red-700`(#b91c1c) 压在 #09090b 上约 **2.99:1**、`text-amber-900` 约 **2:1**，老年用户基本读不出。另有两处直接写死色号：`box.tsx:303` 图标 `color="#b91c1c"`、`:375` 删除钮 `tint="#b91c1c"`；还有一处 `HealthInfoCard` 的「删除」用 `text-destructive` + `color={--destructive}`，而深色档 `--destructive` 是 `hsl(0 62.8% 30.6%)`≈#7f1d1d，压在深色卡面上 **≈2:1**。

**为什么 §2.10 的深色预检没抓到**：那轮看的是五屏常态屏，而**当前云端演示库 4 条 seed 药里没有一条触发错误卡**（`openedOverdue` 要「开封日 + 180 天 < 今天」，`2026-08-18` 那条约等于 2027-02-14 才超期），失败卡只在断网/停库时出现。**深色预检要专门验「异常态」**，光看正常屏会漏掉一整类颜色。

**这条是 mobile 自己的偏差，不是跟 web 学来的**：`grep -rn "bg-red-\|border-red-\|text-red-\|bg-amber-\|text-amber-" packages/web/src --include=*.tsx`（排除 test）**零命中**——web 全走语义令牌（`AnswerCard.tsx:31-32`、`EmergencyCard.tsx:26-31` 是 `border-risk-lN/35 bg-risk-lN/15 text-risk-lN`）。改后 mobile 与 web 语义一致，只是把两端落不了的 `/alpha` 换成算好的 `*-tint` 实色（§7-7 那条坑）。

**改法（不写死色号，全并到 T5-e 补的 risk 令牌上）**：

- 错误/失败卡 → `border-risk-l4 bg-risk-l4-tint` + 文字 `text-risk-l4`；图标与 `tint` 改读 `useUnstableNativeVariable("--risk-l4")`。
- 告警卡（拍照质量、安全提示）→ 壳子 `border-risk-l3 bg-risk-l3-tint`，**正文用 `text-foreground`**：`text-risk-l3`(#c2662f) 压在 `--risk-l3-tint`(#f6e8e0) 上只有约 **3.3:1**，够不上正读对比；描边+底色带出色相，文字本身也写着「照片质量可能影响识别」，不靠颜色表意（§6 第 4 条）。裸行的告警文字（相互作用、未满足原因）同样改 `text-foreground`。
- 成功态 ✓ → `text-risk-l1`；探测页三态 → `text-risk-l2 / l1 / l4`。

**对比度是算出来的**（逐通道 WCAG 相对亮度）：`text-risk-l4` 压 `--risk-l4-tint` = 浅 **4.69:1** / 深 **5.26:1**；压卡面（白 / #09090b）= **5.86:1 / 6.0:1**；`text-foreground` 压 L3 tint = **15.8:1 / 16.5:1**。四档 tint 的深浅两档观感已由 §2.10 第 6 条在模拟器确认过。

**取证**：`npx tailwindcss -i src/global.css -o out.css`（content 走 `tailwind.config.js` 的 `./src/**`）→ `text-risk-l1..l4`、`bg-risk-l3-tint`、`bg-risk-l4-tint`、`border-risk-l3/l4`、`text-foreground` **各 1 条规则**，且 `--risk-l4` 在 `:root`（#b23b3b）与 `@media (prefers-color-scheme: dark)`（#e0685f）**两处都有值**。`npx expo export` 后的 `.hbc`（6,979,585B）UTF-8 探针：`text-risk-l4` 9、`bg-risk-l4-tint` 6、`border-risk-l4` 7、`text-risk-l1` 1、`text-risk-l2` 1 —— 反向 `bg-red-50` / `border-red-300` / `text-amber-900` / `text-red-700` / `#b91c1c` / `text-destructive` **全 0**。⚠️ 这只到「产物里换干净了」，**屏幕观感仍要装机看**。

### 第三条：草稿页物理返回的语义没在界面上说一句（已补，§6 第 15 条）

`drafts/[id].tsx:347-352` 补一句「按返回键不会丢掉这份草稿，回到上一步还能继续核对其它草稿；但这页上还没提交的修改不会保留。」**这句的两个半句都是核对过代码的**：录入屏压在草稿屏下面（expo-router 原生栈，09-29 那个 `intake_ok` 落 `drafts` 步的修复就是它的前提），返回后草稿列表还在；而本页的填写是 `useState`（:104 `initialConfirmState(payload)`），屏幕出栈即销毁。

## 2.12 真机反馈的两条缺陷（10-03，Host=`Robot`，代码侧 + 模拟器按键级实测）

用户 10-02 夜真机（装 20:54 版）提了两条：**① 「灰色还会跳出来」**（附截图：弹窗里胶囊是「20:00 已服」、「确认已服」整条灰着，弹窗却还在）；**② 「编辑时间没法输入数字」**。两条都已定位、修掉、在模拟器上实测验过。

### 第一条：提醒弹窗关不完 / 灰态还跳出来 —— 入队 effect 的依赖带了 `queue`

**根因**（不是「没做置灰判断」，`ReminderModal.tsx:69` 的 `disabled={!nextPending}` 是对的，灰是它看见的全已服）：

1. `index.tsx` 那条「到点仍 pending 就入队」的 effect，依赖是 `[groups, queue, enqueue]`；
2. 在弹窗里点「确认已服」→ `confirmRecord()` 同步调 `dequeue()`；
3. `queue` 一变，effect **立刻重跑**，而乐观更新在 `onMutate` 里排在 `await cancelQueries(...)` 之后（异步），这一刻 `groups` 还是旧的 pending，且该计划已不在队列 → **同一计划被原地重新入队**；
4. 队列非空 → 自动弹出 effect 又把 `reminderPlanId` 指回它 → 弹窗再开；
5. 随后乐观更新落地，缓存变 `taken` → 重绘成截图那样：胶囊「已服」+ 三个钮全灰。

同一条依赖也解释了 10-02 记的「连点 6 次 ✕ 仍在弹」：✕ → `dequeue()` → effect 重跑 → 该计划仍到点 pending → 马上回队。**web 侧 `routes/patient/Home.tsx:93-99` 依赖只有 `[groups]`（带 eslint-disable），所以这是 mobile 移植时多加一个依赖造成的回归，不是两端同源。**

**改了三处**（`app/packages/mobile/src/app/(patient)/index.tsx`）：

| 改法 | 说明 |
|---|---|
| 入队 effect 依赖去掉 `queue`，队列当前值走 `useReminderQueue.getState().queue` | 与 web 同语义；不吃闭包旧值，也不会因 `dequeue` 重跑 |
| 自动弹出 effect 加「死队首」兜底：队首计划已无可操作时点就 `dequeue()` 丢掉再看下一个 | 数据竞态下万一进了一个全已服的计划，也不会开出死弹窗 |
| 卡上「处理提醒」在**无任何 pending 时点**时不再渲染按钮，改静态行「今日已全部记录」 | 用户口径：「完成了就不该弹出来」。这是 mobile 独有差异，登记进本节末清单 |

**模拟器实测**（x86_64 / API 36 / 1080×2400，装 10-03 08:22 版）：

⚠️ **前置一条**：这台 AVD 的时区是 GMT（`persist.sys.timezone=GMT`、`vendor.qemu.timezone=Unknown/Unknown`，非 root 改不动），guest 时钟读到 00:2x → 六个时点一个都没到点 → 队列根本不弹。用 `cmd alarm set-time $(( $(date +%s%3N) + 8*3600*1000 ))` 把 guest 时钟推到 08:3x（同一瞬间 +8h，日期仍是 10-03，与服务端 `today` 对得上），`auto_time` 先置 0、验完复原 1。**真机不需要这一步。**

| 步骤 | 结果 |
|---|---|
| 冷启动进今日页 | 自动弹「该服药了 · 苯磺酸氨氯地平片」，「确认已服（08:00）」是**可点的**（不是灰态） |
| 依次点 ✕ 关三个 | 队列按序推进：氨氯地平 → 二甲双胍 → 格列吡嗪；**关掉最后一个后 +2s / +8s 屏幕节点里再无「该服药了」**（改前这里是「关不掉」） |

### 第二条：计划弹窗「时 / 分」四框敲不进数字 —— 受控值被补零回写

**根因**（`PlanModal.tsx` 的 `setTimePart` + `joinPart`）：框的 `value` 是从规范串 `HH:MM` 切出来的**两位**数字，而 `onChangeText` 收到的是「整框新文本」——

- 敲数字：`"08"` + `"2"` = `"082"` 超 `maxLength={2}` → **RN 在按键落地前就整条拒掉，`onChangeText` 根本不触发**；
- 退格：`"08"` 删成 `"0"` → `joinPart("0","00")` 又补零回写成 `"00:00"` → 框里恒为两位。

两条合起来 = **永远删不到一位、也永远打不进第二位**，四个框全是死的。`HealthInfoCard` 的年 / 月框各存自己的原始串，所以没这问题——只有这一处。

**改法**：`times` 状态从 `string[]` 改成 `{hour,minute}` 原始串数组，框里显示**用户敲出来的原文**；规范 `HH:MM` 只在 `isTimePartsValid()`（校验）和 `onSave`（提交）时拼，交给服务端的仍是与 web `type="time"` 同形的两位串。非法值仍走行内中文提示 + 禁保存，不静默。

**按键级取证**（`时间点 1 小时` 框，逐步回读 `uiautomator` 节点值）：

```
聚焦 → "28"    退格 → "2"    退格 → ""    敲 2 → "2"    敲 0 → "20"
时间点 1 分钟   退格 → "0"    退格 → ""    敲 3 → "3"    敲 0 → "30"
20:30 合法 → 行内提示消失；填 28 时提示「按 24 小时制填 0–23 时 / 0–59 分」在位
```

⚠️ **取证方法学一条**：`input tap` 落在两位文本的正中 = 光标插在两位之间，第一遍按键序列因此读出 `"28"` 这种怪值（退格删掉的是前一位、插入位置在中间）。**判可编辑性要先 `input keyevent KEYCODE_MOVE_END` 再退格**。改前用同一串按键的对照，用 node 复现 `setTimePart` 语义跑过：`08` → 退格 → `00` → 再退格 → `00` → 敲任意数字 → 恒 `00`。
